01 / Context

01Overview

The Blogs category on Railway's template hub is its quietest — 65 templates against 940 for AI/ML. But "quiet" isn't the same as "open": Ghost alone accounts for roughly 3,600 of the category's deploys across nine near-duplicate listings, because it's a real one-click admin panel and nothing else there competes on that ground.

Ghost (9 listings)
~3.6K
WordPress (4)
~1.6K
Comment widgets
~770
Next.js/Astro + CMS
114

That last row is the gap. Only two listings exist (next-wp, a Next.js + headless WordPress starter, and a Next.js + Strapi blog), and both need two or three separate services to run — a Next.js frontend, a CMS backend, sometimes its own database. Neither is actually lighter than Ghost; they're just newer.

Thesis — ship the first "modern stack" blog template that is genuinely a single service. Payload CMS 3 runs as a Next.js plugin, not a separate backend, so the whole thing — admin panel, API, and frontend — is one Next.js app plus one Postgres plugin.

02 / Scope

02Goals & non-goals

Goals

  • One-click deploy to a working blog: an admin login, a published sample post, and a live index page — no code changes required.
  • Exactly two Railway resources: the app service and a Postgres plugin. No queue, no worker, no second app.
  • SEO and syndication out of the box: per-post meta tags, sitemap.xml, and an RSS feed — table stakes for a blog that competitors here mostly skip.
  • Uploaded media survives a redeploy (a Railway Volume, not the container's ephemeral disk).

Non-goals

  • Newsletter delivery / paid memberships — that's Ghost's strongest ground and out of scope for v1.
  • Multi-author roles beyond Payload's built-in admin/editor split.
  • Import tooling from WordPress or Ghost.
03 / Audience

03Target user

A developer who already has (or is about to build) a Next.js product — very plausibly someone who just deployed Railhead — and needs a blog or docs section for marketing, SEO, or changelog purposes. They want to write in a real admin UI, not hand-edit MDX files in git, but they also don't want to run a second service just to do it.

04 / System

04Architecture

One Railway service, one managed plugin. Payload's admin panel, its REST/GraphQL/Local API, and the public-facing blog all render from the same Next.js process — there is no network hop between "the CMS" and "the site" because they're the same app.

07 / Sequences

07Core flows

Authoring

  1. Author logs into /admin (Payload's built-in auth against the users collection).
  2. Drafts a post in the Lexical editor; images upload straight to the mounted volume.
  3. Publishing sets status = published and publishedAt, and triggers an afterChange hook.

Rendering

  1. The frontend (app/(frontend)) reads posts through Payload's Local API — a direct in-process function call, not an HTTP round trip to itself.
  2. Post pages use Next.js's on-demand revalidation: the afterChange hook from the authoring flow calls revalidatePath for the post's URL and the index page, so a publish is live within seconds without a full rebuild.

Syndication

  1. /sitemap.xml and /rss.xml are route handlers that query published posts through the same Local API and serve XML directly — no separate generation step, always current.

09 / Delivery

09Repo & deployment topology

A single Next.js application — no monorepo, no workspaces:

  • src/payload.config.ts — collections, Postgres adapter, plugins (SEO, Lexical)
  • src/collections/ — Posts, Categories, Media, Users
  • src/app/(payload)/ — Payload's generated admin routes
  • src/app/(frontend)/ — the public blog: index, post pages, sitemap, RSS
  • Dockerfile — pinned build image with sharp's native dependencies

Postgres is attached as a Railway plugin and wired in via a reference variable (${{Postgres.DATABASE_URL}}); a Railway Volume is mounted at /app/media for uploads — both declared in .railway/railway.ts.

10 / Hardening

10Security

  • /admin is protected by Payload's own session auth; there is no separate reverse-proxy password layer to keep in sync.
  • PAYLOAD_SECRET is generated per-deploy, never checked into the repo or hardcoded in a default.
  • Public networking is disabled on the Postgres plugin by default — only web reaches it, over the private network.
  • Upload MIME-type and size limits are enforced in the media collection config, not left to defaults.
